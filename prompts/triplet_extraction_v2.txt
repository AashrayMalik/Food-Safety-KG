Notes on relations added back for full coverage:
- The prov: relations (wasAssociatedWith, used, wasGeneratedBy,
  wasAttributedTo, wasInfluencedBy) model provenance links: an
  AdulterationAct's responsible operator and targeted food, an
  Adulterant's generation by that act, an IncidentFinding's attribution
  to a FoodBusinessOperator, and a SpreadEvent's upstream trigger.
  Note fflo:wasGeneratedBy is reused with two different domain/range
  pairs — (fflo:Adulterant, fflo:AdulterationAct) in the ACT stage and
  (fflo:SpreadEvent, fflo:TransformationEvent) in the SPREAD stage —
  pick based on which stage the event belongs to.
- fso:isPerformedOn, fso:isPerformedAt, fso:isResultOf,
  fso:relatesToProperty, fso:isMeasuredIn, fso:hasSampleType, and
  fso:hasLocation model the lab-analysis chain (Analysis on a Sample,
  at a Laboratory, producing an AnalysisResult tied to a Property; a
  Measurement expressed in a UnitOfMeasure; a Sample's SampleType and
  Location). fflo:isPerformedAs bridges an fflo:LaboratoryTest to its
  fso:Analysis. fflo:hasNumericValue attaches the literal numeric value
  to an fso:Measurement node — do not invent any other numeric-value
  predicate.
- fflo:hasIntentionality classifies an AdulterationMethod as
  Intentional/Negligent/Incidental (object type fflo:IntentionalityLevel).
  fflo:commonIn links an Adulterant to the fflo:GeographicRegion where it
  is prevalent. fflo:propagatesTo is the heuristic SupplyChainStep ->
  SupplyChainStep spread edge.
- lkif:created_by links an fflo:FoodStandard to the fflo:RegulatoryBody
  that created it.

TASK

Given a source text chunk, extract all FFLO-relevant triples using only
the schema above. Many real-world claims are not single facts — they
are events with multiple attributes at once (an adulterant, a detection
method, a regulatory clause, a location). Do not force these into one
triple; decompose them into multiple triples sharing one synthetic ID,
reified as the correct FFLO event class for that stage (see EVENT
LINKING).

OUTPUT FORMAT

Return ONLY this JSON object — no markdown fences, no commentary:

{
  "snippet_id": "<provided snippet_id>",
  "triplets": [
    {
      "subject": "...",
      "subject_type": "...",
      "subject_id": "",
      "predicate": "...",
      "object": "...",
      "object_type": "...",
      "object_id": "",
      "confidence": 0.95,
      "evidence_span": "...",
      "event_id": "",
      "event_class": "",
      "polarity": "affirmed",
      "mismatch_note": ""
    }
  ],
  "notes": ""
}

Field rules:
- predicate: FFLO/FKG relation from schema, or "UNMAPPED" if no schema relation fits
- confidence: 0.9-1.0 = explicit, 0.7-0.89 = inferred, 0.5-0.69 = plausible. Below 0.5 — do not extract
- event_id: shared across triples from the same event/claim instance, format ev_<topic>_<NNNN>, omit ("") for standalone triples
- event_class: the FFLO class this event_id instantiates, omit if event_id is omitted
- polarity: "affirmed", "negated", or "hedged"
- evidence_span: verbatim substring (≤ 15 words) from the target chunk
- subject_id / object_id: fill with entity name for structural nodes NOT appearing verbatim in the text; omit ("") for named entities that DO appear
- mismatch_note: only if predicate is "UNMAPPED", describe the natural-language relation
- notes: under 200 characters

If no triples are present, return {"snippet_id": "...", "triplets": [], "notes": ""}.

DATATYPE PROPERTIES

Use the following object types exactly when extracting datatype properties.

- fflo:hasNumericValue -> xsd:decimal
- fflo:hasDefinition -> xsd:string
- fflo:tableLabel -> xsd:string
- fflo:hasScientificName -> xsd:string

Rules

- Use xsd:decimal only for literal numeric values attached via fflo:hasNumericValue.
- Use fso:Measurement for quantities with units (for example "2.5 mg/kg"), then attach the numeric component using fflo:hasNumericValue.
- Use xsd:string only for literal text values such as definitions, scientific names, or table labels.
- Never type literal values as ontology entities.


CANONICAL RELATION NAMES

Always use the canonical relation names defined in the schema.

Do not output aliases, abbreviations, or semantically similar predicate names.

Examples of invalid aliases include:

- fflo:hasIngredient -> use fkg:hasIngredient
- fflo:hasSubCategory -> use fflo:hasSubcategory
- fflo:definition
- fflo:definedAs
- fflo:hasDescription
- fflo:conformsTo -> use fflo:compliesWith
- fflo:hasAdditiveFunction
- fflo:hasTechnologicalFunction
- fflo:hasTechnicalFunction -> use fflo:hasFunction
- fso:hasNumericValue -> use fflo:hasNumericValue
- Bare limit predicates such as hasLimit, hasMaximumLimit, hasMinimumLimit, hasAcidityLimit, hasFatLimit, hasResidueLimit, hasAlcoholLimit, hasPermissibleLimit, etc.

If the source expresses one of these concepts, map it to the corresponding canonical FFLO relation. Never emit an alias in the output JSON.

RULES

- Every triple must be traceable to an explicit evidence_span quoted from the source text.
- Use ONLY schema entity types and relations listed above. If nothing fits, use predicate "UNMAPPED" with mismatch_note — never invent a new type or relation name.
- Never use a bare limit relation (hasLimit, hasAcidityLimit, etc.) — always decompose per Example 3.
- Reuse the same event_id across all triples describing one real-world event, tagged with the correct event_class for that stage.
- Use "negated" for explicit denials, "hedged" for conditional/modal/disjunctive language, "affirmed" otherwise.
- For disjunction, extract one triple per disjunct, both marked hedged.
